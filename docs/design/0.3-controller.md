# 0.3: the controller

Status: phase 1 implemented on the `next` branch (PRs #13–#21). Agreed on 2026-10-26:
- no standalone agents;
- agents are declared in the controller config by token hash;
- agents cache their config and key on disk;
- the coordinator is renamed to **controller**;
- the controller's config is a YAML file;
- a unit does not say where it runs;
- only the controller notifies anyone outside ferryman, and only when its rules say so. Agents send it events and never notify on their own, not even when the controller is unreachable;
- the UI is out of scope: a rewrite comes in a later feature branch. Until then the existing UI keeps working against whatever state the controller still exposes.

## Why

In 0.2, each agent holds its own pools, units and transfers, and the coordinator only shares keys and arbitrates transfer claims. Running `media-tv` on three hosts means three agent configs that drift apart. Nothing sees the whole picture, so nothing can act on what agents report.

In 0.3, the controller holds the config and hands each agent its part. Agents report back, and the controller decides what to do. Phase 1 (this document) moves the config, and moves events and notifications to the controller. Phase 2 lets rules act as well as notify: retry, restart, escalate.

## Config model

A **unit** says *what* is mounted: the drive, its key pool and how it is read. A **binding** says *how one agent runs it*: where it is mounted, as which uid, with what cache and servers. The same unit can be bound differently on a Proxmox host, inside an Emby container and on a Talos node.

### controller.yaml

```yaml
listen: {host: 0.0.0.0, port: 8470, forwarded_allow_ips: "*"}
state: /var/lib/ferryman-controller
ui: {enabled: true, user_header: X-authentik-username}
rclone: {binary: rclone}            # key probes
notify: {...}                       # channels and rules: see Events and notifications
tuning: {...}                       # every agent's, field by field overridable per agent
defaults:                           # built-in < these < (unit | agent defaults) < binding
  vfs_cache_mode: full
  buffer_size: 16M
  uid: 1000
  gid: 1000

pools:
  uploads:
    keys_dir: /etc/ferryman/keys
    keys: [sa-01@proj.iam.gserviceaccount.com, sa-02@proj.iam.gserviceaccount.com]
    probe: {interval: 3600}         # drive: first (default) | rotate; or drive_id: <id>

units:                              # WHAT: no paths, no hosts
  media-tv:
    drive_id: 0AAAAAAAAAAAAAAAAAA
    pool: uploads
    vfs_read_chunk_size: 128M
  media-movies:
    drive_id: 0BBBBBBBBBBBBBBBBBB
    pool: uploads

agents:
  pve-01:                           # a Proxmox host: mounts, serves, uploads
    token_sha256: <hex>
    defaults: {cache_max_size: 50G, cache_min_free_space: 200G}
    units:
      media-tv:
        mounts: [{path: /pool/google/media-tv}, {path: /srv/media/tv, read_only: true}]
        serve: [{type: webdav, addr: ":8081", htpasswd: /etc/ferryman/htpasswd}]
      media-movies:
        mounts: [{path: /pool/google/media-movies}]
    transfers:
      tv-uploads: {unit: media-tv, source: /pool/incoming/tv, schedule: "*/15 * * * *"}

  emby-01:                          # inside the Emby container: read-only, its own uid
    token_sha256: <hex>
    units:
      media-tv:
        mounts: [{path: /media/tv, read_only: true}]
        uid: 1001
        buffer_size: 64M            # this host only: override of the unit's read policy

  talos-01: &talos                  # three identical nodes share one binding
    token_sha256: <hex>
    units:
      media-tv: {mounts: [{path: /var/lib/drive/media-tv}]}
  talos-02: {<<: *talos, token_sha256: <hex>}
  talos-03: {<<: *talos, token_sha256: <hex>}
```

### Where each 0.2 setting goes

| 0.2 | 0.3 |
|---|---|
| unit `backend`, `drive_id`, `pool`, `options` | `units.<u>` |
| unit `vfs_cache_mode`, `vfs_read_chunk_size`, `vfs_read_ahead`, `buffer_size`, `warm` | `units.<u>`, overridable in a binding |
| unit `mounts`, `serve`, `uid`, `gid`, `cache_max_size`, `mount_args` | binding `agents.<a>.units.<u>` |
| `defaults.*` | controller `defaults`; the host fields (uid, gid, cache_max_size, cache_min_free_space, dir_mode) also in `agents.<a>.defaults` |
| `transfers.*` | `agents.<a>.transfers` (a transfer reads that host's files) |
| `pools.*` (local) | controller `pools` (local pools are gone) |
| `tuning` | controller `tuning`, overridable field by field in `agents.<a>.tuning` |
| `notify` | controller only: channels and rules (agents never notify) |
| `health` | controller (sent to every agent) |
| `hostname`, `paths`, `api`, `rclone` | the agent's bootstrap file |
| `coordinator: {url, token_file}` | bootstrap `controller: {url, token_file}` |
| coordinator `agents.<a>.pools` | gone: an agent may lease the pools of the units bound to it |

### Precedence

- **Host fields** (uid, gid, cache_max_size, cache_min_free_space, dir_mode): built-in < controller `defaults` < `agents.<a>.defaults` < binding.
- **Unit policy** (read settings, warm): built-in < controller `defaults` < unit < binding. An agent's `defaults` never override a unit's policy; only a binding for that unit does. That stops a host default from silently changing one unit.
- `read_settings()` reports `binding` as a source, alongside `unit`, `defaults` and `built-in`.

### The agent's bootstrap file

```yaml
# /etc/ferryman/agent.yaml
controller: {url: https://ferryman.example.org, token_file: /etc/ferryman/token}
hostname: pve-01                    # optional: $FERRYMAN_HOSTNAME, else the host name
paths: {state: /var/lib/ferryman, cache: /var/cache/ferryman, logs: /var/log/ferryman, runtime: /run/ferryman}
api: {listen: {host: 0.0.0.0, port: 8470}}
rclone: {binary: rclone, log_level: INFO}
```

Everything here describes the machine and is needed before the agent can reach the controller. An agent config containing `units`, `pools` or `transfers` fails to load with a message pointing to `ferryman migrate`.

### Validation

The controller rejects a config that fails any of these at load. On a reload, it keeps serving the previous config, logs the error, and raises `config.invalid`:
- names are valid, and every reference resolves: binding → unit, transfer → a unit bound on the same agent, unit → pool;
- the field validators (Mount, Serve, Transfer);
- the cross-field rules, checked on each unit plus binding combined: nfs needs `vfs_cache_mode` writes or full; read settings need a mount or server; `vfs_read_ahead` needs full cache mode; read-only binds match the primary mount's FUSE options;
- serve port clashes within each agent;
- **sync overlaps, across agents and within one** (stricter than 0.2's runtime claims, which only compared agents: a sync on one host that contains another of its own transfers is refused too): a `sync` whose destination contains, or is inside, another transfer's destination on the same drive. The controller takes `{hostname}` as the agent's name and cuts a destination at `{env:…}` (it can't see an agent's environment) and at time placeholders, so an uncertain case counts as a clash. This was the coordinator's runtime claim check; now that the controller sees every transfer, it moves to load time, and runtime claims (`/v1/claims`, `claims.json`, `claim_blocks`) go away.

The agent checks what needs the host, each time it applies a config:
- placeholders (`{hostname}`, `{env:NAME}`);
- `Layout.check_paths`: system trees, ferryman's own paths, nesting, transfer sources, secret-file modes;
- port clashes with its own `api.listen`.

A rejected config is not applied. The agent keeps running the previous one and reports the rejection, which the controller raises as `agent.config_rejected`.

## The agent's slice

For each agent, the controller renders a **slice**: the parts of the config that agent needs, resolved. That is its bindings merged with their units and defaults, its transfers, the tuning and health settings, and the names of the pools it may lease. Notification settings are not in it: agents don't notify. No key material is included; keys are still leased separately.

```json
{"schema": 1, "version": "9f2c…", "agent": "pve-01",
 "units": {"media-tv": {"unit": {…resolved unit…}, "set_by": {"buffer_size": "binding"}}},
 "transfers": {…}, "pools": ["uploads"], "defaults": {…}, "tuning": {…}, "health": {…}}
```

`set_by` records whether each read setting came from the unit or the binding, so the agent's status can say so.

In the code, a controller unit is `UnitSpec`. `Unit` stays the flat, per-host unit the agent runs.

- `version` is a hash of the rendered slice. Editing another agent's binding leaves this agent's version unchanged, so it isn't woken for nothing.
- `schema` changes only when the shape of the slice does. An agent refuses a schema it doesn't know, keeps what it has, and says so in its report.

On receipt, the agent builds the flat `Config` that 0.2 code already runs on: bootstrap plus slice. That leaves `UnitSupervisor`, `TransferRunner`, `Tuner` and `Layout` largely unchanged.

## Protocol

The API version moves to `/v2`. Agents and controller upgrade together; a 0.2 agent gets a clear 410 error from a 0.3 controller.

| Method | Path | |
|---|---|---|
| GET | `/v2/config?version=<v>` | Long poll: answers at once with the slice when its version differs from `v`, else after `watch_timeout` with `{"version": v}` |
| POST | `/v2/events` | A batch of events from the agent's outbox, each with its sequence number; answers with the highest sequence stored |
| PUT | `/v2/report` | As `/v1/report`, plus `config: {version, state: applied\|pending\|rejected, error, pending: [...]}` |
| GET/POST | `/v2/pools/...`, `/v2/commands...`, `/v2/tune-lock/...` | As `/v1` |

**Reloading the controller.** It re-reads its config on SIGHUP, and also checks the file's modification time every 10s. That covers Kubernetes Secret updates, which replace the file in place. If the new config is valid, every agent whose slice changed is woken.

**Unknown or revoked token.** The agent never stops its units because of a 401. A typo in a token hash must not unmount a host. It keeps running what it has, records the failure as an event for the controller to pick up once it's accepted again, and keeps retrying. To decommission an agent, first give it no units (`units: {}`), then remove it.

## Applying a config on the agent

The agent compares the new effective config with the running one.

**What counts as a unit change.** The unit's **spec** is everything its rclone process uses:
- the resolved unit fields (backend, drive_id, options, mounts, serve, mount_args);
- `read_settings()` and `resolved()`;
- `cache_min_free_space`, `dir_mode`, `health.stat_timeout`;
- `rclone.binary` and `rclone.log_level`.

A unit restarts only if its spec changed. A new key in its pool isn't a change: a lease reaches a running unit with `backend set`, as rotation does. Moving a unit to another pool is one, and restarts it.

**Order of operations:**
1. Validate, as above. On failure, stop and report the rejection.
2. Start new units.
3. Restart units whose spec changed. A unit with a transfer running on it is left alone until that run ends: a restart would abort the upload. Until then it shows as `pending: restart after transfer <t>`.
4. Stop removed units. This unmounts them, lazily after the usual timeout if a mount is busy. A unit that a running transfer still uses waits for the run to end.
5. Transfers: a new one is scheduled; a changed or removed one finishes its current run first, then its runner is replaced or dropped. A config change never kills a run.
6. Tuning and health settings apply in place; scheduled tasks restart.
7. Pools: start watching new pools; stop watching unused ones and forget their keys.
8. Save the new slice to the cache and report `applied`, or `pending` while waits remain.

Mounts that didn't change are never touched.

## The cache

- `<paths.state>/controller/slice.json` (0600) holds the last applied slice.
- `<paths.state>/controller/keys/<pool>/<key>.json` (0600, root-only) holds the current leased key. It is the same file rclone reads, moved from the tmpfs runtime directory to the state directory so that it survives a restart. Superseded keys are deleted as soon as the agent moves off them, as today.

**At startup:**
1. Ask the controller for the slice, with a short timeout (10s).
2. If that fails and a cache exists, start from the cached slice and key, reporting `cached` until the controller is back; it then confirms the cached slice or applies the current one.
3. If that fails and there is no cache, start nothing and retry with backoff. The agent serves no API until it has a config, so probes and the CLI get no answer: a Kubernetes pod stays not ready, and systemd restarts the agent when its start times out, and it keeps waiting.

The cache is only replaced by a newer applied slice, and it is never deleted automatically. The key cache means a root-only key file sits on disk, the same exposure a 0.2 local pool had.

## Key probes

Probes (0.2.x) need a shared drive to upload to. The controller now knows every unit, so a pool can take that drive from its units instead of naming one:

```yaml
pools:
  uploads:
    probe:
      interval: 3600
      size: 1K
      drive: first          # default: the drive of the first unit (in config order) on this pool
      # drive: rotate       # each probe uses the next drive among the pool's units, in turn
      # drive_id: 0AAAA…    # a specific shared drive; overrides `drive`
```

- **`first`** gives the same drive every time, which is predictable.
- **`rotate`** spreads probe files across drives, and keeps working if one drive's permissions change.
- **`drive_id`** suits a dedicated scratch drive, kept apart from media.
- The controller refuses at load a probing pool with no `drive_id` whose units have no drive.

## Events and notifications

Agents keep emitting the events they emit today (`unit.failed`, `transfer.failed`, `pool.rotated`, `tune.drift`, …). From 0.3 they deliver every event to the controller and notify no one. The controller stores events, evaluates its rules, and sends any notifications.

### Delivery from the agent

- Every event gets a sequence number from the agent. The number is kept in the state directory, so it keeps counting across restarts.
- Events go into an **outbox** in the state directory, `<paths.state>/controller/outbox.jsonl`. It is bounded: the newest 10,000 events or 7 days, and when full the oldest are dropped and the drop is itself recorded as an event.
- A sender loop posts batches to `/v2/events` and removes what the controller acknowledges. If the controller is down, events wait in the outbox and arrive late, with their original times.
- Because the controller stores events by (agent, sequence), a batch sent twice is stored once.
- The agent keeps its own recent history for `ferryman events`. The per-report `events` list goes away.

### Replaying a backlog

When the controller is reachable again, after a controller outage, a network split or the agent's own restart, the agent sends its outbox from the oldest event.

- **Order:** events are sent strictly in sequence, in batches of up to 500. A batch is removed from the outbox only once the controller acknowledges it. A failed post is retried, with backoff up to 60s, starting from the first unacknowledged event, so nothing is skipped and nothing is reordered.
- **Durability:** an event is appended and flushed to the outbox before anything else happens with it. An agent crash or restart loses nothing already written, and sequence numbers carry on from the last one stored.
- **Overflow:** if the outbox fills up during a long outage (10,000 events or 7 days), the oldest are dropped. A `events.dropped` event records how many and from when, so the gap is visible on the controller.
- **Event time, not arrival time:** the controller evaluates replayed events in order using the time each one *happened*. A `count: 3, within: 15m` rule counts failures 15 minutes apart by when they occurred, not three that arrived together.
- **Problems that are already over:** a problem that opened and closed entirely inside the backlog (`unit.failed`, then `unit.recovered`, all while the controller couldn't hear) is not sent as an alarm. It goes out as one summary per agent and channel, for example "while unreachable (14:02–14:31): media-tv failed 3×, recovered 14:20". Problems still open at the end of the replay are sent as normal.
- **Duplicates:** the controller stores events by (agent, sequence), so a batch resent after a lost acknowledgement is stored once.
- **Controller-side view:** an agent reports how many events wait in its outbox (`outbox` in its report, `ferryman_events_undelivered` in its metrics). The controller's own `agent.silent` for an outage closes once the agent reports again.

The trade-off of controller-only notifications is that **nothing notifies while the controller is down**; events arrive when it's back. Watch the controller itself from outside ferryman. Prometheus can scrape its `/healthz` and `ferryman_controller_*` metrics, and every agent exports `ferryman_controller_reachable`. Agents never fall back to notifying on their own.

### Events the controller raises itself

| Event | When |
|---|---|
| `agent.silent` / `agent.recovered` | No report for `agents_silent_after` (default 2m) / reports again |
| `agent.config_rejected` | An agent refused its slice (the error is attached) |
| `config.invalid` | A reload of controller.yaml failed; the previous config stays in force |
| `pool.exhausted` / `pool.recovered` | Every key in a pool is capped / one is usable again |
| `probe.recovered` | A probe returned a key early |

### Rules

```yaml
notify:
  batch: 60                         # collect matches this long, send them as one message per channel
  repeat: 6h                        # an open problem is re-sent at most this often
  channels:
    ops:
      smtp: {host: smtp.example.org, port: 587, starttls: true, user: ferryman, pass_file: /etc/ferryman/smtp.pass,
             from: ferryman@example.org, to: [ops@example.org]}
    ha:
      webhook: {url: https://ha.example.org/api/webhook/ferryman, headers: {}}
  rules:
    - name: errors                  # 0.2's behaviour: every error, once, then every `repeat`
      match: {severity: error}
      send: [ops]
    - name: crash-loop
      match: {kind: unit.failed}
      when: {count: 3, within: 15m, per: [agent, subject]}   # 3 failures of one unit on one agent in 15 minutes
      send: [ops, ha]
    - name: unit-down-everywhere
      match: {kind: unit.failed}
      when: {agents: all-bound, within: 5m, per: [subject]}  # every agent bound to the unit failed it
      send: [ha]
    - name: quiet-agent
      match: {kind: agent.silent}
      send: [ha]
```

- **`match`** selects events by `kind` (exact match or a glob such as `unit.*`), `severity` (a minimum level), `agent` and `subject`. These can be combined; all must hold.
- **`when`** is optional; without it, any match fires. With it, the rule fires once the condition holds within the window:
  - `count: N` means N matching events;
  - `agents: N | all-bound` means distinct agents, where `all-bound` is every agent bound to the subject unit.
- **`per`** keeps a separate count for each value of the fields listed, for example one count per agent and unit.
- **Problems and recoveries:** a firing rule opens a problem keyed by rule and `per` values. It is re-sent at most every `repeat` while open. The matching recovery event (`unit.recovered` for `unit.failed`, same agent and subject) closes it, and the recovery is sent only if the problem was. This is the 0.2 notifier's logic, applied per rule.
- **`send`** names channels. Matches for one channel within `batch` go out as one message: a network blip that restarts every unit on every host is one email.
- **Mail** goes out over SMTP from the controller. It usually runs in a container with no `sendmail`; `sendmail:` stays available as a channel type for hosts that have one.
- **State:** events are kept in `<state>/events.jsonl` (`events.retention_days`, 30; trimmed at start and daily), so rule windows survive a restart and a later UI can show history. Open problems are kept in `<state>/problems.json`, so a restart doesn't re-send everything.

### State for a later UI

The controller's state API exposes events, open problems, each rule's last firing and each channel's last delivery error. Phase 1 adds no UI for them; the UI rewrite will.

## Rename: coordinator → controller

The rename is a clean break, with no aliases; `ferryman migrate` and the release notes explain it.
- **CLI:** `ferryman coordinator` becomes `ferryman controller`.
- **Module:** `coordinator.py` becomes `controller.py`, and `coordinator_pool.py` becomes `controller_pool.py`.
- **Files:** the config is now `/etc/ferryman/controller.yaml` and the state directory `/var/lib/ferryman-controller`. Pool state and probes move with the directory; `ferryman migrate` prints the `mv`.
- **Environment:** `FERRYMAN_CONTROLLER_CONFIG`.
- **Deployment and docs:** the systemd unit, compose service, k8s directory, metrics prefix (`ferryman_controller_*`) and wiki all follow. The UI only gets the name change.

## `ferryman migrate`

```bash
ferryman migrate --coordinator coordinator.yaml pve-01=pve-01/config.yaml emby-01=emby.yaml ... --out ferryman-0.3
```

It reads the 0.2 configs and writes a controller config, plus a bootstrap file for each host:
- **Units:** each host's units are split into a unit and a binding. If two hosts define the same unit name with different unit settings, migration fails and lists the differences. Rename one, or make them agree.
- **Read settings:** where all hosts agree, a read setting becomes the unit's or the controller default. Where they differ, it becomes per-binding overrides.
- **Pools:** local pools become controller pools. The keys need copying to the controller host; the tool lists which files go where. Existing coordinator pools and probes carry over.
- **Tokens:** the existing coordinator tokens are kept. A host that had none gets a new token, printed with its hash.
- **Notify:** each host's mail and webhook settings become controller channels. Duplicates are merged, and its `level`, `batch` and `repeat` become one default rule that behaves as 0.2 did.
- **Tuning:** it comes from the first host, and differences are reported.

## Deployment

- **Docker Compose:** the controller is no longer an optional profile. A single host runs both services, and the agent waits for the controller to be healthy.
- **Kubernetes:** the agent DaemonSet's config shrinks to the bootstrap file. Units and bindings move into the controller's config Secret. Per-node tokens stay as they are.
- **systemd:** `ferryman-controller.service` replaces `ferryman-coordinator.service`, with the same sandbox. rclone is needed only for probes.

## Phase 1 PRs

Work happens on a `next` branch, merged to `main` for 0.3.0. 0.2.x fixes go to `main` meanwhile.

1. **Rename** coordinator → controller across code, CLI, files, manifests and docs. This is mechanical, and nothing else changes yet.
2. **Config models:** `Unit` / `Binding` / `AgentSpec` / `ControllerConfig` / `AgentBootstrap`, the resolver (slice → flat `Config`), load-time validation including sync overlaps, and a rewritten example config and tests.
3. **The controller serves slices:** `/v2`, `/v2/config` long poll, versioning, reload, pools derived from bindings, `probe.drive` (`first` / `rotate`); claims removed.
4. **The agent runs from its slice:** bootstrap-only config, fetch at startup, the cache with the key in the state directory, start from cache during an outage. A config change still means an agent restart at this point.
5. **Live apply:** the spec diff, the operation order above, waiting for running transfers, and reporting `pending` and `rejected`.
6. **Events to the controller:** the agent outbox and `/v2/events`; the controller's event store and its own events (`agent.silent`, `agent.config_rejected`, `config.invalid`, pool events). Agents stop notifying.
7. **Notifications on the controller:** channels (SMTP, webhook, sendmail), rules (`match`, `when`, `per`, `send`), problems, recoveries and batching, plus the 0.2-equivalent default rule.
8. **`ferryman migrate`.**
9. **Deployment and docs:** compose, k8s, systemd, the wiki, release notes, then 0.3.0.

The UI is not part of phase 1. The existing page keeps working where its data still exists. A rewrite (per-agent and per-unit views, config state, events, problems, rules) comes in its own feature branch.

## Phase 2 (outline): rules that act

Rules gain actions besides `send`, carried out through the commands the controller already sends:
- `retry` a failed transfer after a delay;
- `restart` a unit;
- `rotate` a pool;
- `run` a transfer on another agent.

Each action is limited per window, so a broken rule can't loop, and every action is recorded as an event. The rule format above is designed so these slot in next to `send`.
